Imagine you deploy a ML model that predicts if a financial transction is faudulent
data keeps updating, transction patterns change, customer behavior evolves, data entering model starts looking differently from what is was trained on

model doesnt crash, accuracy goes down
-> model degradation

PROBLEM SOLVED: detecting it

Platform contnuously monitors deployed model, identifies potential drift
is retraining required, train candidate models, evaluate them against existing producton model and deploy replacement only when criteria is met

1. Data Ingestion
New incoming data enters the platform, validate it and prepare for inference

2. Model serving
A trained model makes predictions through API
Record inputs, predictions and actual outputs

3. Monitoring
Monitor input distributions
prediction distributions and model performance

4. Drift Detection
Alibi Detect compares incoming data against a reference distribution and identifies stats that change 

5. Retrain Decision
The system evaluates whether drift is sufficiently significant to justify retraining

6. Automated retraining 
Airflow orchestrates a pipeline that prepars data, trains candidte models and evaluates them

7. Model evalution and registration
MLFlow tracks experimentats, parameters, metics and model versions
Candidate must passed predefined criteria

8. Deployement and verification
The approved model is depoyed in a DOcker container
Verification and Monitoring

What stands out
1. Drift is not the same as accuracy
A model can experience data drift without accuracy decreasing and the other way around
Monitoring system can distinguish both

2. Retrinaing is not automatically beneficial 
A newly trained model can perform worse than the existing production model
there needs to be a promotional policy

3. Production deployement is risky
Model fails to load, 
predictions are invalid,
performance detoriates,
immediately after deployement

implement safeguards, deployement verification and rollback

4. System needs evidence that is works
Deliberately introduce changes into incoming data, 
observe detection process, 
trigger retraining and 
demonstrate if new model actually improves performance

Concepts that matter
1. Data Drift
Suppose model was trained using reference dataset
Where features have values that have changed significantly after a few months
Thus, data drift where the stat dist of the input features

2. Concept Drift
Fraudsters have a new technique developed 
transctions above x are marked as Fraud,
thus they keep their transactions below x
the relationship between input and target features has changed

Data drift: (P(X)) changes
Concept drift: (P(Y|X)) changes

3. Model performance degradation
Even when accuracy degrades, the model continues to produce predictions
Thus, monitoring is needed

4. Reference Data vs Production Data
Use Alibi Detect
Reference Data: The dataset or representative sample against which we establish what a normal dist looks like
Production Data: The new obs entering our deployed model

Drift Detector compares the both

Thus, model should be able to distinguish between
Detecting changes in incoming data
Confirming whether model performance has deteriorated
Deciding whether retraining is justified

Dataset chosen
Credit Card Fraud Detection Dataset
1. Represents real-world classification problem
2. Contains numerical transaction features
3. Fraud is a minority class, making it useful for class imbalance
4. Simulate changes in behavior is importance
5. Can evaluate whether retraining actually improves performance

Features:
1. Time: seconds elapsed between the first transactions and the current one
2. Amount: transaction Amount
3. V1-V28: Numrical features produce through PCA transformation
4. Class: Whether the transaction is fraus(1) or legit(0)

PCA transformed features are anonymous

Usage of Dataset
Creating three distinct data env:
1. Reference/ Training data
Historical transactions used to train our initial model and establish baseline feature distribution

2. Production/ Incoming data
transactions arriving after deployement. Initially these will resemble the original data.

3. Drift Simulation data
deliberately introducing distribution changes to miukate changing transaction behavvior and test monitoring system.

IMP:
Randomly splitting the data and then use the test set to train replacement models: no
Instead, seperate datasets for:
Initial model Training
